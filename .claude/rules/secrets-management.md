# 機密情報の取り扱い

本インストラクションは、本パッケージをインストールしたプロジェクトにおいて、Coding Agent が認証情報や機密情報をどのように扱うべきかを定義する。Agent がコンテキストに読み込む情報、上流モデルプロバイダーへ送信する情報、ファイルに書き出したりコミットしたりする情報のすべてに適用される。

## 「機密情報」の対象

以下は機密情報として扱う：API Key、Personal Access Token、Service Account Key、パスワード、秘密鍵・証明書、セッショントークン、および慣例的にそれらを保持することが想定されているファイル（`.env*`、`credentials.json`、`*.key`、`*.pem`、`*.p12`、`~/.ssh/id_*`、`~/.aws/credentials`、`~/.config/gcloud/*`、`~/.azure/*` など）。

## 絶対に含めてはならない (MUST NOT)

以下は、Agent のコンテキスト、コミット内容、コミットメッセージ、ブランチ名・タグ名、Pull Request の説明文・コメントのいずれにも含めてはならない：

- 本番環境の認証情報（値・構造を問わず）
- ローテーション不可能な認証情報（共有パスワード、マスターキー、長命な秘密鍵など）
- 広範な権限を持つ認証情報（admin、削除、フルアクセス権限など）

これらはいかなる利便性のためにも例外としない。

## 原則として避けるべき（例外的に許容可能）

dev / local 環境の認証情報も、原則として Agent のコンテキストには含めない。以下のすべてを満たす場合に限り、例外的に許容する：

- 顧客データ・本番データが存在しない環境であり、VPN や認証基盤（IdP）等で外部アクセスが制限されていること
- 代替となるテストフィクスチャやモックが存在せず、明確な必要性があること
- 作業後に即座にローテーション可能であること
- スコープが限定的（read-only または狭い権限）であること
- 漏洩時の被害が許容範囲内であること

いずれかを満たさない場合は、作業を止めて利用者に確認する。

## 比較的安全に扱える情報

実際の値を含まない形であれば、以下は共有・コミットしても問題ない：

- 設定ファイルの構造（値を `***` やプレースホルダーに置換したもの）
- 環境変数の **キー名のみ**（値は含めない）
- `.env.example` のようなプレースホルダー入りテンプレート
- 認証情報の値を除去したエラーログ
- ホスト名・ポート番号・外部から到達できないローカル専用の値（例: docker-compose の DB パスワード）

## 見落としやすい混入経路

以下もチェック対象とする。意図せず機密情報が露出しやすい経路である：

- コミットメッセージへの値の記載（例: 「API キーを sk-... に変更」）
- `.git/config` の認証情報付き URL（例: `https://token:ghp_xxxx@...`）
- `.gitmodules` の認証情報付きサブモジュール URL
- ブランチ名・タグ名への混入（例: `fix/update-key-sk_live_xxx`）
- Pull Request の説明文・コメント
- CI/CD 設定ファイル内のハードコード（プラットフォームのシークレット機構を使わず直接記述しているケース）

## 推奨する検出・予防策

Agent は以下の制御が整備されていることを前提に動作する。欠けているものがあれば、無断で作業を進めず、フォローアップとして提案する：

- `.gitignore` に機密系ファイル（`.env*`、`*.key`、`*.pem`、`credentials.json`、`secrets.json` など）を含める
- pre-commit フックで [gitleaks](https://github.com/gitleaks/gitleaks) 等のシークレット検出ツールを実行する。`git commit --no-verify` はこれを迂回するため、Agent は `--no-verify` を使用してはならない
- サーバー側シークレットスキャン（GitHub Secret Protection の Push Protection が利用可能ならそれを、そうでなければ CI で gitleaks を実行）を整備する。`on: push` 単体ではすでにリモートに到達した漏洩を止められないため、`pull_request` と組み合わせて必須ステータスチェックに登録する

## 実際の機密情報に遭遇した場合

プレースホルダーでない本物の認証情報と思しき値を Agent が読み込んだ場合、以下を遵守する：

1. その内容をコンテキストとして使い続けない
2. 値を利用者に復唱せず、外部送信や別ファイルへの書き出しもしない
3. 発見を利用者に知らせ、ローテーションを促す

## 認証情報の「生成」を求められた場合

API キー、トークン、サービスアカウントキーの作成、既存クレデンシャルのローテーションは、Agent が自律的に実行してはならない。コマンド案の提示にとどめ、実行は利用者に委ねる。

## プロジェクト固有のオーバーライド

本パッケージをインストールした各プロジェクトは、以下のような具体事項を上位で定義することが期待される：どの環境を「本番」とみなすか、どのシークレットストアを正とするか、ローテーションをどこで運用するか、どのスキャナ設定を採用するか。本パッケージはあくまでデフォルトを定めるもので、プロジェクト側の指示と衝突する場合はプロジェクト側が優先する。
